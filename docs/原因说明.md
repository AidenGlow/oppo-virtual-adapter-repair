# OPPO 互联为什么可能让 TUN 模式无法联网

## 案例提供了什么线索

用户截图对应 Clash Verge Rev 的 [讨论 #6712](https://github.com/clash-verge-rev/clash-verge-rev/discussions/6712)，发表于 2026-04-03。帖主报告：原本正常的 TUN 在安装 OPPO 互联并出现 `utun8` 后断网；删除网卡后重启会重现，卸载 OPPO 后才恢复。

这些前后变化指向 **OPPO 互联相关虚拟网卡参与了该环境下的冲突**。单独移除网卡后会重现，说明需要考虑仍在运行或启动的创建方；仅凭帖子还不能定位具体进程、服务或驱动行为。`utun8` 是案例中的名字，排查时应核对本机设备说明，不能按这个名字批量删除网卡。

## 为什么可能表现为整机断网

TUN 可以理解为代理接收流量的入口，实际 Wi-Fi / 以太网则负责把处理后的连接送往互联网。Mihomo 的 [auto-route](https://wiki.metacubex.one/config/inbound/tun/#auto-route) 会将全局流量路由进 TUN；[auto-detect-interface](https://wiki.metacubex.one/config/inbound/tun/#auto-detect-interface) 用于自动选择流量出口，官方文档建议多出口环境手动指定网卡。

**结合上述机制，一个合理的技术推断是：**OPPO 新增虚拟网卡后，网络接口环境发生变化，代理的出口识别或实际路由可能受到影响。此时流量被送进 TUN，却未能从真正联网的接口发出，就可能表现为开启 TUN 后大范围无法联网。

这是对案例的机制解释。要确定故障机器上究竟是出口误选、路由异常还是其他驱动交互，需要同时检查故障前后的路由表、接口信息及代理日志；原帖截图未提供这些证据，不能将某一个环节写成已经确认的根因。

## 本工具的两种方式分别针对哪里

| 方式 | 排障思路 | 操作前提与影响 |
| --- | --- | --- |
| OPPO DLL 改名 | 尝试改变 OPPO 对指定 Wintun 组件的加载，从虚拟网卡创建相关组件这一侧绕开冲突；这是社区提出的排障办法 | 必须先登录并连接手机；可能影响新设备或部分连接方式；修复及恢复后均需重启 |
| 指定代理出口网卡 | 关闭出口自动选择，明确让代理从实际联网的 Wi-Fi / 以太网发出连接，用于排查出口选择受干扰的情况 | 先退出代理客户端，再手选正确网卡；完成后重新打开；换网络或订阅刷新后可能需要重新配置 |

第二种方式使用以下配置关系，网卡名称以本机为准：

```yaml
interface-name: "Wi-Fi"  # 顶层：实际联网的网卡
tun:
  auto-detect-interface: false
```

`interface-name` 是 Mihomo 的[全局出站接口](https://wiki.metacubex.one/config/general/)，与 `tun` 同级；`tun.device` 指的是 TUN 自身的名称，不能用它代替实际出口网卡。工具保留用户选择、备份和最终确认；遇到问题可按[使用说明](使用说明.md)恢复。
